# Files Photos and Locker copy boundary

Source inspected: `tcc-operations/repos/thecreatingco-site`, revision `1d24b08ad6e072a5984d21d94c243a61b9d7271b`, `locker/core.js` and `locker/locker.js`. This repository is a historical mirror, so this records the inspected source contract rather than claiming current production deployment parity. No external source files were modified.

Locker core v1 stores `tcc-locker` database / `files` records on its own origin. Native records contain `id,name,type,size,app,created,updated,meta,blob`; `get()` returns the original Blob. The original Locker UI's Download control reads that Blob and downloads the original name. No native bulk backup/import format is established in this source. The legacy bridge's exact origin allowlist does not include Hole's Netlify origin; this package neither changes that allowlist nor accesses production storage through an unqualified bridge.

Files now has All files, Photos, and Imported Locker files views over the same local identities. Photos displays at most 60 lazy raster thumbnails per list render; every matching file retains its accessible named row and original preview/download/tools. Thumbnail URLs are revoked on rerender/close; unsupported or broken image previews preserve downloadable bytes. SVG and unsupported image formats retain file controls without an active-document preview.

The Locker view retains the original `https://thecreatingco.com/locker/` route. Its explicit path is: open original Locker, download chosen originals, choose Imported Locker files, import those files into Hole. Hole records this as **user-declared download provenance**, not verified access to another origin or an ongoing sync. Originals in Locker are untouched. Core backups retain the resulting provenance; plain original-file downloads do not invent metadata absent from the native download.

`HoleFiles.openView('photos'|'locker'|'all')` is available for shell entry points. `HoleFiles.importLockerRecords(records)` accepts supplied records using the inspected native schema, validates Blob/size/type/origin assumptions, and copies originals through acknowledged Core saves with source ID/app/timestamps/meta. It does not fetch remote records or grant access. Failed validation happens before any record in the supplied selection is written; individual storage failure can retain earlier successfully acknowledged copies and never deletes the source.

Verification: six file-platform tests pass, including identity-preserving filters and native-schema bytes through Core close/reopen. `tests/verify-files-browser.mjs` passes installed headless Chrome 155: decoded photo thumbnail, unchanged file identity across views, manual Locker import, actual download byte equality, and reload. With `HOLE_LOCKER_CORE` pointing to the inspected `locker/core.js`, it also executes that original storage API in a disposable local browser origin, reads its real stored Blob, imports it through the adapter, and verifies both source and copy bytes. This is native source-contract verification at a test origin; it does not establish production cross-origin permission, Safari, physical mobile, or historical production-profile migration.

Run the opt-in browser check with `HOLE_PLAYWRIGHT_MODULE` pointing to an installed Playwright module and optional `HOLE_CHROME` executable / `HOLE_LOCKER_CORE` source path. Existing user browser profiles are never opened or cleared.
