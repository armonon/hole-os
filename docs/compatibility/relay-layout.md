# Selected project positions through Relay

`src/relay-layout.js` implements one explicit layout-sync path: selected material positions from a saved local arrangement. It does not synchronize native editor state or restore historical content. Existing private preference/workspace/memory behavior remains separate.

The versioned `hole.relay-layout/1` payload has a name and 1–50 numbered slots. Each slot contains a material label and only x/y/depth/rotation/scale. Bounds are ±6,000 for position/depth, ±360 degrees and 0.1–10 scale. Asset IDs, version IDs, project IDs, resource references, pins, window state, runtime IDs, editor checkpoints, navigation, drafts and credentials are excluded. Upload selection displays each selected label and geometry. Transfer uses the existing private `scene` record type with empty references and optimistic expected revision; the server's existing 64 KiB JSON bound also applies.

The UI mounts as `HoleRelayLayouts.mount({client,ctx,host,projectId,snapshot,refresh})` from Relay. It offers selected saved-arrangement upload, creation or revision of a private remote layout and explicit destination mapping. Queuing does not send: the existing Send queued changes control performs transport. Nothing subscribes to changes or applies layouts automatically. Unrecognized/invalid remote layout values remain on the service and are reported instead of applied.

The destination must be an existing local project. Every remote slot maps to a distinct existing local asset placement in that project. A second review shows before/after geometry before Apply. Review identities and geometry are sealed to the current session; edited or reconstructed plans require a new review. Application rereads current placement metadata and changes only those placement geometry fields; it retains resource identity, existing latest/pinned policy and version pin, current asset heads and all drafts. It neither opens files/editors nor creates a historical-version selection. Preserving a pre-existing pin does not change it to a remote version.

## Conflicts and durable local application

Remote concurrency uses the existing durable Relay queue: a failed network request retains the exact pending payload; restart reopens it; a stale expected revision yields a conflict with both local and current remote values available. Explicit review can retain remote state or enqueue a replacement against the reviewed revision. Original conflict payloads remain in resolved history. The layout module validates received schema again before local application.

Core has no general multi-record transaction. The module checks all local revisions before writing and then uses Core's revision checks for each write. Before mutation it persists a `hole.relay-layout-journal/1` settings record containing the complete reviewed plan and original placements. Each write has a durable intent followed by its receipt. A failure reports the exact acknowledged count; an uncertain write is recorded and automatic undo refuses to guess. This is explicit, inspectable partial-application recovery, not atomic multi-placement commit. An existing application journal prevents accidentally repeating the same plan.

Journal review exposes originals, confirmations, errors and uncertain writes. Undo applies only original geometry and refuses any subsequent local placement edits. Undo has its own intent/receipt journal and incomplete-state reporting. Files, pins and drafts are not rollback targets. When an uncertain write exists, the current implementation retains the journal for manual inspection; it does not claim an automatic conflict-resolution wizard for uncertain local writes.

## Evidence

`node --test tests/relay-layout.test.mjs` passes six checks: payload allowlist/bounds, geometry-only apply/undo, local revision conflict, injected mid-apply storage failure with original/uncertain state retained, undo refusing newer work, mutable metadata preserving pins/resources, and altered review identities or geometry requiring a new review.

`node scripts/verify-relay-layout-browser.mjs` passed Chrome 156.0.8078.48 with two disposable persistent profiles, real Core IndexedDB and the real local HTTP service. Actual UI capture/queue, destination mapping/review/apply and journal undo retain local version pins, newer committed bytes and an unsaved draft. An offline queued layout at x=300 survives profile close/reopen while the other profile writes x=400. Sync retains that conflict; explicit replacement x=350 commits while the original x=300 payload remains. A local placement change after review blocks application; reviewing again succeeds.

The `HOLE_LAYOUT_SHELL_URL=http://127.0.0.1:5193` integrated-shell path also passed after the review-seal fix, exercising actual Relay connection, project selection, mapping and apply controls and preserving its local draft. This mode binds the disposable service to port 8787, which the shell CSP explicitly allows; it fails if that port is occupied instead of stopping another service. The source-only test uses an ephemeral port. No CSP relaxation is needed. This is local service/browser evidence, not hosted-account deployment, physical-device, native-window or general application-state synchronization qualification.
