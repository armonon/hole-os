# Explicit recovery after a failed initial window checkpoint

A durable native recovery can exist without a `runtime:<instanceId>` record when the initial window checkpoint fails. Previously `HoleStudioRecovery.find` only enumerated runtime records, so that recovery was absent from the picker after reload. The original reproduction used actual retained Glyph, refused only the initial runtime record, edited advance width 600→777 and explicitly saved native recovery. The built app then reported `{runtime:0,recoveries:1,unloadPrevented:false,discoverableAfterReload:0,reopenedAdvance:"600"}`. Recovery bytes remained stored but were not discoverable through normal opening. The original disposable-profile script/log are `/tmp/studio-orphan-recovery-review.mjs` and `/tmp/studio-orphan-recovery-review.log`.

`src/studio-recovery.js` now offers a conservative fallback only when the runtime record is entirely absent. It uses an explicit allowlist of shipped `hole.{luma,glyph,form,stemdeck,animate,ghost}-binding/1` schemas, not asset names or inferred MIME types. The instance/key, requested asset, exact bound version, sole granted input, project identifier and bounded nonempty recovery envelope must agree. Core must return the active exact source and its matching version ownership. Running instances, malformed/other-app runtime records, unknown schemas, unreadable/trashed sources, mismatched bindings and multiple-input grants are excluded. Discovery synthesizes an in-memory runtime-shaped recovery choice and never writes, deletes or replaces a saved record. Opening still requires the existing explicit Recover choice; the adapter validates the native recovery bytes when mounted.

ScenePilot orphans are deliberately excluded: its source-ID-to-media mapping is not present in the bridge binding record, so it cannot be safely reconstructed from resource IDs. Unsupported and ambiguous records remain untouched. Orphan discovery does not restore absent window geometry, authorize new resources, recover native request payloads, or guarantee recovery after process termination before durable acknowledgement.

The coordinator separately added an unload guard for an initial runtime-checkpoint failure. That guard warns before reload until the runtime checkpoint is successfully retried; orphan discovery also supports already-existing records and deliberate reload after the warning.
