# Runtime close and window checkpoint retention

Close now makes the mounted input surface inert before serialization, durable runtime persistence and adapter unmount. Failed serialization/storage/unmount restores the prior inert and iframe pointer styles and leaves the live instance available. Ordinary checkpoints do not freeze input this way. The frame's scoped bridge authority is not changed by this admission guard.

Actual Chrome156 testing exposed two nested-frame details: the active child input could still receive keyboard events when only its ancestor became inert, and compositor hit testing could accept a pointer event immediately after style mutation. The runtime explicitly moves focus outside the closing surface, disables iframe pointer events, and waits two animation frames (bounded100ms fallback for inactive documents) before taking the snapshot. All prior styles are restored on failure. Direct text focus is restored; exact caret restoration inside an opaque child is not provided by the parent runtime. Independent browser review verifies normal Tab navigation returns to its live field and keyboard editing works after refusal; immediate caret restoration is not claimed. No physical-device or assistive-technology qualification is claimed.

The old generated build reproduced a late typed edit after its runtime snapshot (`/tmp/hole-wave14-runtime-before.log`). `scripts/verify-runtime-close-browser.mjs` exercises real shell/Core storage with a held/refused runtime write, actual keyboard and pointer input against both a text surface and opaque iframe, restored editing after refusal and retry. Source run passes `/tmp/hole-wave14-runtime-source.log`; final generated check passes without source overrides (/tmp/hole-wave14-runtime-built.log). The keyboard check follows normal document Tab order rather than assuming a fixed number of stops across the surrounding workspace. Two additional runtime regressions cover held persistence, adapter refusal and preservation of existing inert state.

A separate failure existed when an editor mounted successfully but its first window checkpoint failed: the shell removed its host after swallowing failed cleanup, potentially leaving a running hidden instance. Window controls and the running-studio entry now exist before that checkpoint; failure keeps the editor visible and offers Retry window checkpoint. No forced discard or revocation is performed. `scripts/verify-window-checkpoint-browser.mjs` reproduced zero visible frames before the fix and verifies actual Glyph editing, durable native recovery bytes, successful retry and normal Close afterward. Source log `/tmp/hole-wave14-window-source.log` passes; final generated check passes without source overrides (/tmp/hole-wave14-window-built.log).

A native editor that cannot initialize still needs its existing source/error diagnosis; retaining a visible failure does not repair corrupt source data or bypass recovery refusal. Direct adapter close still uses its own flush contract. The shared guard does not grant arbitrary child code new authority or guarantee suppression of programmatic writes.
